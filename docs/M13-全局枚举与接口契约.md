## 4. 订单状态拆分

订单相关状态**不允许**使用单一字段混合表达。必须拆分为三个独立字段：

| 字段 | 用途 | 表 |
|------|------|-----|
| `order_status` | 业务履约状态 | `biz_order` |
| `pay_status` | 余额支付状态 | `biz_order` |
| `refund_status` | 退款状态 | `biz_order` |

### 4.1 订单状态 `order_status`

| 值 | 常量名 | 含义 | C端展示 |
|----|--------|------|---------|
| 0 | `PENDING_PAY` | 待支付 | "待支付" |
| 1 | `ACCEPTED` | 已接单（待制作） | "已接单/待制作" |
| 2 | `MAKING` | 制作中 | "制作中" |
| 3 | `READY` | 待取餐 | "待取餐" |
| 4 | `COMPLETED` | 已完成 | "已完成" |
| 5 | `CANCELLED` | 已取消 | "已取消" |

> **制作流转（2026-06-25 修订，详见 M15 §6.4）**：**串行制作**（一次一单，无并发产能）。`1→2`（开始制作）系统自动推进（制作中无单时推进队列最早单）；`2→3`（制作完成/通知取餐）制作中订单点"通知取餐"直接流转，扫码/手输订单号仅作为兜底；`3→4`（完成/归档）三途径：店员点完成按钮 / 待取餐 4 小时超时（PickupTimeoutTask 每分钟扫，仅处理 `3`）/ 凌晨 4 点兜底（DailyFinalizeTask，处理昨日及更早 `1/2/3`）。**不再扫码核销**。支付成功时算 `estimated_ready_time`（预计取餐时间）。

### 4.2 支付状态 `pay_status`

| 值 | 常量名 | 含义 |
|----|--------|------|
| 0 | `PAY_PENDING` | 待支付 |
| 1 | `PAY_SUCCESS` | 支付成功 |
| 2 | `PAY_TIMEOUT` | 支付超时关闭 |
| 3 | `PAY_REFUNDING` | 退款处理中 |
| 4 | `PAY_REFUNDED` | 已全额退款 |

### 4.3 退款状态 `refund_status`

| 值 | 常量名 | 含义 |
|----|--------|------|
| 0 | `REFUND_NONE` | 无退款 |
| 1 | `REFUND_PROCESSING` | 退款处理中 |
| 2 | `REFUND_SUCCESS` | 退款成功 |
| 3 | `REFUND_FAILED` | 退款失败 |

### 4.4 订单取消场景

| 场景 | 触发方 | 允许状态 | 退款行为 |
|------|--------|----------|----------|
| 用户主动取消 | C端 | `order_status=0` | 无需退款（未支付） |
| 支付超时 | 定时任务 | `order_status=0, pay_status=0` | 无需退款 |
| 管理员取消 | 管理后台 | `order_status=0` | 无需退款 |
| 管理员/门店取消已接单订单 | 管理后台/门店端 | `order_status=1, pay_status=1` | 仅允许一次整单全额退款 |

**统一规则**：
- 余额支付成功即视为门店已接单，订单进入 `ACCEPTED`，不再执行人工接单。
- 用户支付后不允许主动取消。
- V1.0 不支持部分退款；每张订单最多成功执行一次整单全额退款。

## 5. 门店状态

| 值 | 常量名 | C端可见/浏览菜单 | 即时单 | 预订单 | 说明 |
|----|--------|-----------------|--------|--------|------|
| 0 | `RESTING` | ✅ | ❌ | ✅ | 休息中 |
| 1 | `OPEN` | ✅ | ✅ | ✅ | 营业中 |
| 2 | `PAUSED` | ✅ | ❌ | ✅ | 暂停即时接单 |

**统一规则**：所有非 `del_flag=1` 的门店均可进入并浏览菜单。`RESTING` 和 `PAUSED` 不允许提交即时单，但允许提交预订单。

**营业时间跨午夜**：`open_time` > `close_time` 表示跨日营业（如 18:00–02:00）。

**删除规则**：门店使用逻辑删除（`del_flag`），禁止物理删除。已删除门店的历史订单引用必须保留。

### 5.1 即时单与预订单

| 字段 | 取值/规则 |
|------|-----------|
| `order_type` | `NORMAL` 即时单 / `PREORDER` 预订单 |
| `scheduled_pickup_time` | 预订单必填；即时单为空 |
| 预订单时间范围 | 使用门店 `preorder_min_minutes` / `preorder_max_days` 配置，默认30分钟至7天 |
| 预订单营业校验 | 预约取餐时间必须落在门店营业时间内，支持跨午夜 |

- `OPEN` 门店允许即时单和预订单。
- `RESTING`、`PAUSED` 门店仅允许预订单。
- 预订单支付成功后同样自动进入 `ACCEPTED`，门店端按预约取餐时间安排制作。
- 使用门店 `make_lead_minutes` 配置进入制作窗口的提前量，默认30分钟。

### 5.2 制作配置与订单完成（2026-06-25 修订，详见 M15 §6.4）

| 字段 | 类型 | 默认 | 规则 |
|------|------|------|------|
| `minutes_per_cup` | INT | 3 | 单杯制作时间（分钟），用于估算预计取餐时间 |

- **串行制作**（一次一单，无并发产能概念）；~~`concurrent_capacity`~~ 已去掉
- **预计取餐时间**：即时单 `estimated_ready_time = 支付时间 + (前面排队杯数 + 本单杯数) × minutes_per_cup`；预订单 = `scheduled_pickup_time`
- 「前面排队杯数」= 同店已支付且 `order_status in (1,2)`、按制作队列排序位于本单之前的订单杯数之和
- `biz_order.estimated_ready_time`（DATETIME，可空）：支付成功时算
- **订单完成（`3→4`）三途径**：店员点完成按钮 / 待取餐 4 小时超时（PickupTimeoutTask 每分钟扫，仅 `3→4`）/ 凌晨 4 点兜底（DailyFinalizeTask 扫昨日及更早 `1/2/3→4`）。**不再扫码核销**。

## 6. 规格选项不可变规则

| 规则 | 说明 |
|------|------|
| optionId 不可变 | 每个规格选项有全局唯一、不可变的 `optionId`（雪花ID或UUID） |
| 选项不可删除（有历史引用时） | 若任何订单明细引用了该 optionId，选项不可删除，仅可标记禁用 |
| 可新增选项 | 规格模板允许新增选项，不影响已有订单 |
| 选项名可修改 | name/label 可修改，optionId 不变 |
| 加价可修改 | priceAdd 可修改，但已有订单不受影响（订单是快照） |
| 订单快照 | `biz_order_item.specs` 存储下单时的 optionId + name + priceAdd 完整快照 |

下单时必须校验：optionId 属于商品引用的规格模板、选项处于启用状态、必选规格已选择、单选只能选一个、多选数量位于 `min_select` 至 `max_select`。

## 7. 取餐码设计

### 7.1 双字段分离

| 字段 | 用途 | 唯一性 |
|------|------|--------|
| `pickup_token` | 标签出餐扫码令牌（12位随机字母数字） | 全局唯一，永久 |
| `pickup_display` | 门店当日展示号（字母+3位数字） | 每日每店唯一 |

**生成规则**：
- `pickup_token`：安全随机生成12位字母数字，写入时依赖唯一索引检测碰撞并重试，仅作为出餐兜底扫码凭证；制作中订单主流程通过"通知取餐"按钮（orderId）完成 `2→3`；不再用于 `3→4` 核销
- `pickup_display`：每日每家门店从 `A001` 开始，按 `A001...A999、B001...Z999` 顺序递增，用于屏幕/语音叫号
- `pickup_display` 由支付事务内的 `pickup_sequence` 数据库序列表原子分配，不依赖 Redis
- 即时单的 `pickup_date` 为支付日期；预订单的 `pickup_date` 为预约取餐日期

**防碰撞**：
- `pickup_token` 使用 `uk_pickup_token` 唯一索引
- `pickup_display` + `shop_id` + `pickup_date` 联合唯一约束
- 即使跨年、跨门店也不会碰撞

## 8. 余额支付核心约束

### 8.0 已确认决策

| 决策 | 结论 |
|------|------|
| 充值方式 | V1.0 仅通过 M14 余额账户管理事务手动充值，禁止直接修改余额，C端无充值入口 |
| 初始余额 | 新用户注册后默认余额为 0 |
| 支付密码 | V1.0 不做支付密码，直接扣款 |
| H5 取餐通知 | V1.0 不做 |

### 8.1 扣款原子性

```
使用数据库行级锁：
  SELECT * FROM biz_order WHERE id = ? FOR UPDATE
  校验订单属于当前用户且仍为待支付
  SELECT * FROM c_user_balance WHERE user_id = ? FOR UPDATE
  校验余额 >= 支付金额
  UPDATE SET balance = balance - amount, version = version + 1
  INSERT balance_ledger
  INSERT payment_ledger
  提交事务
```

### 8.2 幂等控制

| 机制 | 实现 |
|------|------|
| 支付幂等键 | `payment_ledger.idempotent_key` = `"{orderId}:pay"` UNIQUE |
| 退款幂等键 | `refund_ledger.idempotent_key` = `"{orderId}:refund"` UNIQUE |
| 库存变更幂等键 | `stock_ledger.idempotent_key` = `"{orderId}:{shopProductId}:{DEDUCT|RESTORE}"` UNIQUE |
| 余额流水幂等键 | 支付/退款使用 `"{orderId}:balance:{PAY|REFUND}"`，充值使用 `"recharge:{requestId}"` |
| 订单提交幂等键 | `biz_order` 使用 `UNIQUE(user_id, submit_key)`，重复提交返回原订单 |

后台库存调整使用 `stock_ledger.idempotent_key = "adjust:{requestId}"`。

### 8.3 并发控制

- 余额：乐观锁（version 字段）
- 库存：条件 UPDATE（`WHERE stock = -1 OR stock >= quantity`）
- 同一订单不允许并发支付（幂等键唯一约束）
- 支付、取消、退款和超时任务必须锁定订单行，或使用带原状态条件的原子 UPDATE，防止状态并发覆盖。

### 8.4 退款重复防护

- 同一订单仅允许一次整单全额退款，不支持部分退款
- `refund_ledger` 幂等键唯一约束阻止重复退款
- 退款前校验 `pay_status = PAY_SUCCESS` 且 `refund_status = REFUND_NONE`
- 退款金额必须等于订单 `total_amount`

## 9. 库存核心约束

### 9.1 原子条件扣减

```sql
UPDATE shop_product
SET stock = CASE WHEN stock = -1 THEN -1 ELSE stock - #{quantity} END
WHERE id = #{id}
  AND (stock = -1 OR stock >= #{quantity});
-- 影响行数 = 0 → 库存不足
```

### 9.2 库存流水

每次库存变更（扣减/恢复/调整）必须写入 `stock_ledger`：
- `shop_product_id`
- `change_type`：`DEDUCT`（扣减）、`RESTORE`（恢复）、`ADJUST`（调整）
- `change_amount`：变更量（正数为增，负数为减）
- `before_stock` / `after_stock`
- `idempotent_key`
- `order_id`（如与订单相关）
- `reason`（后台 `ADJUST` 调整时必填）

### 9.3 取消恢复

- 取消订单时恢复库存：有限库存执行 `UPDATE SET stock = stock + quantity`，无限库存 `-1` 保持不变
- 不限制恢复时的库存上限
- 每个订单商品使用独立幂等键防止重复恢复

### 9.4 库存范围

| 范围 | V1.0 支持 |
|------|-----------|
| 商品级库存（shop_product.stock） | ✅ |
| SKU 规格库存 | ❌ |
| 原料库存 | ❌ |

## 10. 员工与门店多对多

### 10.1 关联表 `staff_shop`

| 字段 | 说明 |
|------|------|
| `staff_id` | 独立门店员工 `shop_staff.id` |
| `shop_id` | 门店ID |
| `is_default` | 是否默认门店（1=是） |

> `staff_shop` 只表达"员工被授权操作哪些门店"，不再保存每店岗位。V1.0 员工端能力以账号启停状态 + 门店授权为准；后续若细分操作权限，应在员工账号/权限组维度设计，不回到每店岗位字段。

### 10.2 规则

| 规则 | 说明 |
|------|------|
| 默认门店 | 首次授权自动成为默认门店，`is_default=1` |
| 多店授权 | 员工可关联多家门店；只要被授权多家即可切换当前门店 |
| 当前门店上下文 | 登录后取 `is_default=1` 的门店，可切换到任一授权门店 |
| 越权防护 | 所有 B端接口必须校验 `当前员工 + X-Shop-Id ∈ staff_shop`，禁止跨门店操作 |
| 无全店绕过 | 员工端账号都必须绑定门店；若依超级管理员不属于员工端身份体系 |
| 授权即时失效 | 每个 B 端请求实时校验 `shop_staff.status`、JWT `token_version` 与 `staff_shop` 关联 |

### 10.3 独立员工账号 `shop_staff`（门店员工小程序）

| 字段 | 说明 |
|------|------|
| `id` | 独立员工 ID |
| `account` | 密码登录账号，UNIQUE |
| `phone` | 员工登录手机号，UNIQUE |
| `password` | BCrypt 密码 |
| `status` | 0正常 / 1停用 |
| `token_version` | 敏感信息变更时递增，旧 JWT 立即失效 |

- `shop_staff` 与若依 `sys_user` 完全独立，不共享账号、密码或 Token。
- 登录流程：手机号/账号 → 查 `shop_staff` → 校验状态与 `staff_shop` 授权 → 签发员工端独立 JWT。
- 门店关系使用 `staff_shop.staff_id`，不再使用 `sys_user.user_id`。
- `refund_ledger` 含审计三字段 `shop_id / operator_id / reason`（NOT NULL，不可变），任何退款必留"谁、在哪店、为何退"。

## 13. monthly_sales 方案

`shop_product.monthly_sales` 字段移除，改为实时查询或日汇总：

**V1.0 方案**：从 `biz_order_item` + `biz_order` 计算：
```sql
SELECT product_id, SUM(oi.quantity) AS sales
FROM biz_order_item oi
JOIN biz_order o ON oi.order_id = o.id
WHERE o.shop_id = ? AND o.pay_time >= ? AND o.pay_status = 1
GROUP BY product_id
```

统计窗口：近30天。可在 Redis 缓存日汇总数据以减少实时查询压力。

## 14. Redis 购物车并发方案

购物车不再使用"整段 JSON 读改写"模式。改用以下方案之一：

**V1.0 方案**：每个购物车条目使用独立 Hash Field

```
Key: cart:{userId}:{shopId}
Hash Fields:
  - shopId → "1"
  - item:{cartItemId} → JSON of single item
  - version → 乐观锁版本号（用于全量替换场景）
```

或使用 **Lua 脚本** 进行原子操作：

```lua
-- 原子添加购物车条目
local cartKey = KEYS[1]
local itemField = ARGV[1]
local itemJson = ARGV[2]
local shopId = ARGV[3]

redis.call('HSET', cartKey, 'shopId', shopId)
redis.call('HSET', cartKey, itemField, itemJson)
redis.call('EXPIRE', cartKey, 604800)
return {ok = "SUCCESS"}
```

## 15. 接口契约统一

### 15.1 URL 前缀

| 端 | 前缀 | 认证 |
|----|------|------|
| C端 | `/api/c/` | Bearer Token（JWT，7天） |
| B端 | `/api/b/` | 独立员工 JWT（身份来源 `shop_staff`） |
| 管理后台 | `/api/admin/` | 若依 Token |

### 15.2 统一分页响应

```json
{
  "code": 200,
  "msg": "查询成功",
  "rows": [],
  "total": 100
}
```

> **注意**：若依原生分页返回不含 `pageNum`/`pageSize`（前端自行管理），保持一致。

### 15.3 统一金额单位

所有金额以**分**为单位（int），前端展示时转为元。

### 15.4 购物车接口必须携带 shopId

```
POST /api/c/cart/add
Body: { "shopId": 1, "productId": 10, "specs": {...}, "quantity": 1 }
```

- `shopId` 必填
- Redis Key 使用 `cart:{userId}:{shopId}`，不同门店购物车相互隔离
- 获取、修改、删除、清空购物车接口均必须携带 `shopId`

### 15.5 规格选择传 optionId

```json
{
  "specs": {
    "1": "opt_abc123",    // 规格模板ID: 选中的 optionId
    "2": "opt_def456",
    "3": "opt_ghi789",
    "5": ["opt_jkl012", "opt_mno345"]  // 多选规格传数组
  }
}
```

后端根据 optionId 计算价格，**不信任前端传来的价格**。
