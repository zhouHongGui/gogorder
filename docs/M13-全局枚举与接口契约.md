## 4. 订单状态拆分

订单相关状态**不允许**使用单一字段混合表达。必须拆分为三个独立字段：

| 字段 | 用途 | 表 |
|------|------|-----|
| `order_status` | 业务履约状态 | `biz_order` |
| `pay_status` | 余额支付状态 | `biz_order` |
| `refund_status` | 退款状态 | `biz_order` |

### 4.1 订单状态 `order_status`

| 值 | 常量名 | 含义 | C端展示 |
|----|--------|------|---------|
| 0 | `PENDING_PAY` | 待支付 | "待支付" |
| 1 | `PAID` | 已支付（待接单） | "等待接单" |
| 2 | `MAKING` | 制作中 | "制作中" |
| 3 | `READY` | 待取餐 | "待取餐" |
| 4 | `COMPLETED` | 已完成 | "已完成" |
| 5 | `CANCELLED` | 已取消 | "已取消" |

### 4.2 支付状态 `pay_status`

| 值 | 常量名 | 含义 |
|----|--------|------|
| 0 | `PAY_PENDING` | 待支付 |
| 1 | `PAY_SUCCESS` | 支付成功 |
| 2 | `PAY_TIMEOUT` | 支付超时关闭 |
| 3 | `PAY_REFUNDING` | 退款处理中 |
| 4 | `PAY_REFUNDED` | 已全额退款 |

### 4.3 退款状态 `refund_status`

| 值 | 常量名 | 含义 |
|----|--------|------|
| 0 | `REFUND_NONE` | 无退款 |
| 1 | `REFUND_PROCESSING` | 退款处理中 |
| 2 | `REFUND_SUCCESS` | 退款成功 |
| 3 | `REFUND_FAILED` | 退款失败 |

### 4.4 订单取消场景

| 场景 | 触发方 | 允许状态 | 退款行为 |
|------|--------|----------|----------|
| 用户主动取消 | C端 | `order_status=0` | 无需退款（未支付） |
| 支付超时 | 定时任务 | `order_status=0, pay_status=0` | 无需退款 |
| 管理员取消 | 管理后台 | `order_status=0` 或 `order_status=1, pay_status=1` | 已支付需退款 |
| 店员拒单 | 门店端 | `order_status=1, pay_status=1` | 需退款 |

## 5. 门店状态

| 值 | 常量名 | C端可见 | C端可下单 | 说明 |
|----|--------|---------|-----------|------|
| 0 | `RESTING` | ✅ | ❌ | 休息中 |
| 1 | `OPEN` | ✅ | ✅ | 营业中 |
| 2 | `PAUSED` | ✅ | ❌ | 暂停接单 |

**统一规则**：所有非 `del_flag=1` 的门店在C端均可见。`RESTING` 和 `PAUSED` 状态展示对应状态标签但不可下单。

**营业时间跨午夜**：`open_time` > `close_time` 表示跨日营业（如 18:00–02:00）。

**删除规则**：门店使用逻辑删除（`del_flag`），禁止物理删除。已删除门店的历史订单引用必须保留。

## 6. 规格选项不可变规则

| 规则 | 说明 |
|------|------|
| optionId 不可变 | 每个规格选项有全局唯一、不可变的 `optionId`（雪花ID或UUID） |
| 选项不可删除（有历史引用时） | 若任何订单明细引用了该 optionId，选项不可删除，仅可标记禁用 |
| 可新增选项 | 规格模板允许新增选项，不影响已有订单 |
| 选项名可修改 | name/label 可修改，optionId 不变 |
| 加价可修改 | priceAdd 可修改，但已有订单不受影响（订单是快照） |
| 订单快照 | `biz_order_item.specs` 存储下单时的 optionId + name + priceAdd 完整快照 |

## 7. 取餐码设计

### 7.1 双字段分离

| 字段 | 用途 | 唯一性 |
|------|------|--------|
| `pickup_token` | 内部唯一核销令牌（UUID短码，8位字母数字） | 全局唯一，永久 |
| `pickup_display` | 门店当日展示号（5位数字，当日门店内递增） | 每日每店唯一 |

**生成规则**：
- `pickup_token`：UUID 取前8位（字母数字混合），全局唯一，用于扫码核销
- `pickup_display`：5位流水号，每日每家门店从 00001 开始，用于屏幕/语音叫号

**防碰撞**：
- `pickup_token` 使用 `uk_pickup_token` 唯一索引
- `pickup_display` + `shop_id` + `date(create_time)` 联合唯一约束
- 即使跨年、跨门店也不会碰撞

## 8. 余额支付核心约束

### 8.1 扣款原子性

```
使用数据库行级锁：
  SELECT * FROM c_user_balance WHERE user_id = ? FOR UPDATE
  校验余额 >= 支付金额
  UPDATE SET balance = balance - amount, version = version + 1
  INSERT balance_ledger
  INSERT payment_ledger
  提交事务
```

### 8.2 幂等控制

| 机制 | 实现 |
|------|------|
| 支付幂等键 | `payment_ledger.idempotent_key` = `"{orderId}:pay"` UNIQUE |
| 退款幂等键 | `refund_ledger.idempotent_key` = `"{orderId}:refund:{seq}"` UNIQUE |
| 库存扣减幂等键 | `stock_ledger.idempotent_key` = `"{orderId}:stock"` UNIQUE |

### 8.3 并发控制

- 余额：乐观锁（version 字段）
- 库存：条件 UPDATE（`WHERE stock >= quantity AND stock > 0`）
- 同一订单不允许并发支付（幂等键唯一约束）

### 8.4 退款重复防护

- 同一订单仅允许一次退款
- `refund_ledger` 幂等键唯一约束阻止重复退款
- 退款前校验 `pay_status = PAY_SUCCESS` 且 `refund_status = REFUND_NONE`

## 9. 库存核心约束

### 9.1 原子条件扣减

```sql
UPDATE shop_product
SET stock = stock - #{quantity}
WHERE id = #{id}
  AND stock >= #{quantity}
  AND stock > 0;
-- 影响行数 = 0 → 库存不足
```

### 9.2 库存流水

每次库存变更（扣减/恢复/调整）必须写入 `stock_ledger`：
- `shop_product_id`
- `change_type`：`DEDUCT`（扣减）、`RESTORE`（恢复）、`ADJUST`（调整）
- `change_amount`：变更量（正数为增，负数为减）
- `before_stock` / `after_stock`
- `idempotent_key`
- `order_id`（如与订单相关）

### 9.3 取消恢复

- 取消订单时恢复库存：`UPDATE SET stock = stock + quantity`
- 不限制恢复时的库存上限
- 幂等键防止重复恢复

### 9.4 库存范围

| 范围 | V1.0 支持 |
|------|-----------|
| 商品级库存（shop_product.stock） | ✅ |
| SKU 规格库存 | ❌ |
| 原料库存 | ❌ |

## 10. 员工与门店多对多

### 10.1 关联表 `staff_shop`

| 字段 | 说明 |
|------|------|
| `user_id` | 若依系统用户ID |
| `shop_id` | 门店ID |
| `is_default` | 是否默认门店（1=是） |
| `role` | 岗位角色：`STAFF`（店员）/ `MANAGER`（店长）/ `ADMIN`（管理员授权） |

### 10.2 规则

| 规则 | 说明 |
|------|------|
| 店员默认一家 | 创建店员时自动分配一家门店，`is_default=1` |
| 店长多店 | 店长可关联多家门店，可切换当前门店 |
| 管理员多店授权 | 管理员可被授权访问多家门店 |
| 当前门店上下文 | 登录后取 `is_default=1` 的门店，可切换 |
| 越权防护 | 所有 B端接口必须校验 `staff_shop` 关联，禁止跨门店操作 |

## 13. monthly_sales 方案

`shop_product.monthly_sales` 字段移除，改为实时查询或日汇总：

**V1.0 方案**：从 `biz_order_item` + `biz_order` 计算：
```sql
SELECT product_id, COUNT(*) AS sales
FROM biz_order_item oi
JOIN biz_order o ON oi.order_id = o.id
WHERE o.shop_id = ? AND o.create_time >= ? AND o.order_status IN (1,2,3,4)
GROUP BY product_id
```

统计窗口：近30天。可在 Redis 缓存日汇总数据以减少实时查询压力。

## 14. Redis 购物车并发方案

购物车不再使用"整段 JSON 读改写"模式。改用以下方案之一：

**V1.0 方案**：每个购物车条目使用独立 Hash Field

```
Key: cart:{userId}
Hash Fields:
  - shopId → "1"
  - item:{cartItemId} → JSON of single item
  - version → 乐观锁版本号（用于全量替换场景）
```

或使用 **Lua 脚本** 进行原子操作：

```lua
-- 原子添加购物车条目
local cartKey = KEYS[1]
local itemField = ARGV[1]
local itemJson = ARGV[2]
local shopId = ARGV[3]

local currentShopId = redis.call('HGET', cartKey, 'shopId')
if currentShopId and currentShopId ~= shopId then
    return {err = "SHOP_MISMATCH"}
end
redis.call('HSET', cartKey, 'shopId', shopId)
redis.call('HSET', cartKey, itemField, itemJson)
redis.call('EXPIRE', cartKey, 604800)
return {ok = "SUCCESS"}
```

## 15. 接口契约统一

### 15.1 URL 前缀

| 端 | 前缀 | 认证 |
|----|------|------|
| C端 | `/api/c/` | Bearer Token（JWT，7天） |
| B端 | `/api/b/` | 若依 Token |
| 管理后台 | `/api/admin/` | 若依 Token |

### 15.2 统一分页响应

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "rows": [],
    "total": 100
  }
}
```

> **注意**：若依原生分页返回不含 `pageNum`/`pageSize`（前端自行管理），保持一致。

### 15.3 统一金额单位

所有金额以**分**为单位（int），前端展示时转为元。

### 15.4 购物车接口必须携带 shopId

```
POST /api/c/cart/add
Body: { "shopId": 1, "productId": 10, "specs": {...}, "quantity": 1 }
```

- `shopId` 必填
- 若与 Redis 中现有 `shopId` 不一致 → 返回错误码 `SHOP_MISMATCH`，**不清空购物车**
- 前端收到 `SHOP_MISMATCH` 后弹窗询问用户是否切换门店并清空购物车

### 15.5 规格选择传 optionId

```json
{
  "specs": {
    "1": "opt_abc123",    // 规格模板ID: 选中的 optionId
    "2": "opt_def456",
    "3": "opt_ghi789",
    "5": ["opt_jkl012", "opt_mno345"]  // 多选规格传数组
  }
}
```

后端根据 optionId 计算价格，**不信任前端传来的价格**。
