## 一、项目背景

**gogorder**：面向奶茶/饮品连锁的**多门店在线点单系统**。

| 端 | 状态 | 接口前缀 |
|----|------|---------|
| C端顾客（uni-app 小程序+H5）：点单/余额支付/取餐 | ✅ 已实现 | `/api/c/` |
| 管理后台（Vue3 PC） | 🟡 部分实现 | `/api/admin/` |
| **门店端（员工操作台）** | 🟡 后端 M10 部分（staff_shop/退款等），`/api/b/` controller 入口在建 | `/api/b/` |

技术栈：Java 21 + Spring Boot 4.0.3（若依 RuoYi-Vue 底层）/ MySQL 8 / Redis 5 / 前端 uni-app(Vue3)。

**本任务**：设计**门店员工小程序**（微信小程序，手机端门店运营台）。

**关键判断**：M10（门店端 PC 看板）此前只有纸面设计；`/api/b/` 入口在建。小程序与 M10 **互补**：PC 屏常亮负责接单提醒+叫号，手机负责移动核销/出餐/运营。

**重要定位**：小程序是员工**主动打开**的操作工具，**不做被动接单提醒**。接单提醒由两个渠道承担：① PC 看板前台常亮（M10，主渠道）；② 飞鹅打印机支付后自动出单（物理提醒）。**完全不做微信订阅消息、不做轮询/声音/振动/超时。**

## 二、门店授权模型

员工端只认证独立 `shop_staff`。`staff_shop` 是多对多授权表，只表示“这个员工可以操作哪些门店”，不再维护每店职务/岗位。

| 维度 | 规则 |
|------|------|
| 员工身份 | 只读取 `shop_staff`，不接受若依管理后台身份 |
| 门店范围 | 可操作门店 = `staff_shop` 授权门店集合 |
| 默认门店 | 首次授权自动成为默认门店 |
| 门店切换 | 授权门店数 > 1 即可切换到任一授权门店 |
| 操作能力 | V1.0 根据账号启停状态 + 门店授权判断；后续需要细分时在员工账号/权限组维度扩展 |

## 三、功能模块（V1.0 MVP）

底部 5 Tab：**工作台 | 看板 | 核销 | 订单 | 我的**

| 模块 | 功能 |
|------|------|
| 登录 | 手机号验证码登录（查 `shop_staff.phone`，风控见 §七）；员工账号密码兜底；首店自动默认且默认门店不可直接取消 |
| 工作台 | 当前门店+营业状态切换、待办计数(待制作/待取餐)、扫码核销入口、今日营收概览 |
| 看板 | 四 Tab，**进入/下拉刷新加载，无轮询/声音/振动/超时**、开始/批量开始/完成制作 |
| 核销 | 扫码核销(`uni.scanCode`)、手动输入 12 位 token（频率限制）；**多杯订单显示总杯数并强制确认全部交付** |
| 订单 | 本店订单列表、详情、制作前取消退款（授权员工，必填原因，service 层门店校验，三项强制控制） |
| 商品 | 商品列表、一键沽清/恢复、库存调整（后续权限组细分） |
| 我的 | 授权多店切换、个人信息(手机号脱敏)、退出 |

## 四、核心业务流程

**制作-核销主流程**（支付成功即自动接单）：
```
order_status: 1待制作 →(开始制作)→ 2制作中 →(制作完成,叫号)→ 3待取餐 →(核销)→ 4已完成
```

**核销校验**：`pickup_token` 存在 + `order_status=3` + 归属当前门店 → 置 4。多杯订单显示总杯数，强制确认全部交付再完成。

**取消退款（授权员工，三项强制控制 + V1.1 告警）：**
- **service 层双重校验**：`cancelPaidOrderWithRefund(orderId, shopId, cancelReason, operatorId)` 先校验操作人的门店授权，再锁单校验订单归属；任一不匹配均返回 403。
- **V1.0 三项强制**：
  1. 每单一次整单全额（`refund_ledger` 幂等键 `{orderId}:refund` UNIQUE）；
  2. **必填退款原因**（`cancelReason` 空 → 抛异常）；
  3. **不可变审计**：`refund_ledger` 记 `shop_id / operator_id / reason`（NOT NULL）。
- **V1.1**：单店单日退款次数/金额阈值告警（V1.0 仅日志监控）。
- 前置：仅 `order_status=1 且 pay_status=1` 可退；制作中(=2)后不可退。

## 五、关键业务约束（继承 gogorder 全局契约）

- **订单三状态**：`order_status`(0/1/2/3/4/5)、`pay_status`(0/1/2/3/4)、`refund_status`。表 `biz_order`/`biz_order_item`。
- **取餐码双字段**：`pickup_token`(12位，核销用) + `pickup_display`(A012，叫号用)。**`pickupToken` 绝不进日志**。
- **余额支付**（非微信支付）：行级锁 + 乐观锁 + 幂等键 + 流水双写。V1.0 仅后台手动充值。
- **库存**：商品级(`shop_product.stock`)，条件 UPDATE 原子扣减 + `stock_ledger` 幂等。
- **越权防护**：`/api/b/` 接口校验 `当前员工 + X-Shop-Id ∈ staff_shop`；退款 service 内再次校验 `operatorId + shopId` 授权和订单归属；不存在全店绕过。
- **退款审计**：`refund_ledger` 含 `shop_id/operator_id/reason`（不可变）。
- **日志**：成功 info / 幂等 debug / 业务失败 warn / 异常 error；门店操作带 `operatorId`；`pickupToken`/验证码/token 不进日志。
- **金额**：分（int）。**响应**：`{code,msg,data}`，分页 `{code,msg,rows,total}`。

## 六、接口设计

统一 Header：`X-Shop-Id`，后端校验 `当前员工 + X-Shop-Id ∈ staff_shop`，越权 403。

**复用 M10 接口**：`GET /api/b/order/board`、`GET /api/b/order/{id}/detail`、`PUT /api/b/order/{id}/start-make`、`PUT /api/b/order/batch-start-make`、`PUT /api/b/order/{id}/complete-make`、`PUT /api/b/order/verify`、`PUT /api/b/order/{id}/cancel-refund`(必传 cancelReason)、`GET /api/b/order/pending-count`、`PUT /api/b/shop/status`、`GET /api/b/shop/revenue-today`。

**新增**：`/api/b/auth/login/sms`、`/api/b/auth/login/password`、`/api/b/shop/mine`、`/api/b/shop/switch`、`/api/b/workbench/today`、`/api/b/shop-product/list`、`/api/b/shop-product/{id}/soldout`、`/api/b/shop-product/{id}/stock`、`/api/b/shop/revenue`、`/api/b/area/board`、`/api/b/area/revenue`。

**幂等契约：**

| 操作 | 幂等机制 | 重复请求行为 |
|------|---------|-------------|
| 开始/完成制作 | 原状态条件 UPDATE | 已是后续状态 → 返回当前状态（不报错） |
| 核销 verify | `WHERE order_status=3 AND pickup_token=? AND shop_id=?` | 已核销 → 返回"已核销"；不存在/错店/状态不符 → 模糊错误 |
| 取消退款 | `refund_ledger` 幂等键 `{orderId}:refund` | 重复 → 返回原退款结果 |
| 库存调整 | `stock_ledger` 幂等键 `adjust:{requestId}` | 重复 → 返回原结果 |
| 沽清 / 营业状态 | 设目标值，天然幂等 | 重复 → 返回当前值 |

## 七、登录与风控（独立 shop_staff）

**身份基础**：独立表 `shop_staff` 保存员工账号、唯一手机号、BCrypt 密码、状态和 `token_version`，与 `sys_user` 完全解耦。流程：手机号或员工账号 → 查 `shop_staff` → 校验状态和 `staff_shop` 授权 → 签发独立员工 JWT。迁移见 `gogorder_v1_0_staff_independent_schema_patch.sql`。

**短信登录风控（必做）：**

| 项 | 规则 |
|----|------|
| 独立验证码池 | `purpose=STAFF_LOGIN`，与 C 端隔离 |
| 发送频率 | 同手机号 60s 内 1 次；同 IP 每日上限 N 次 |
| 手机号枚举防护 | 未在 `shop_staff` 注册的手机号**不发真实验证码**；登录失败统一模糊提示 |
| 验证码尝试 | 同码错误 5 次失效 |
| 一次性消费 | 验证成功立即失效 |
| 登录失败锁定 | 同 IP/账号连续失败 N 次 → 锁定 M 分钟 |
| 禁用即失效 | `shop_staff.status=停用` 或 `token_version` 变化 → 旧员工 JWT 立即失效；移出门店后该店请求立即被拒绝 |

**核销防探测**：手输核销码频率限制（≥10 次/分钟拦截）；错误信息模糊化（统一"核销码无效或当前不可用"）；日志禁记 `pickupToken`。

## 八、非功能需求

| 项 | 要求 |
|----|------|
| **接单提醒** | 小程序**不承担**。渠道：PC 看板常亮(M10) + 飞鹅打印机自动出单。**不做订阅消息/轮询/声音/振动/超时** |
| 看板加载 | 进入页面 + 下拉刷新 |
| 弱网 | 失败本地重试一次；幂等契约保证重复提交无副作用 |
| 性能 | `board` 走 `idx_shop_order_status`；`workbench/today` 一次拉全 |

## 九、技术选型

前端 uni-app(Vue3)，工程名 `gogorder-staff`；扫码 `uni.scanCode`；后端 Spring Boot(若依) + 新建 `controller/b/` + 独立员工 JWT 过滤器 + `X-Shop-Id` 拦截器；认证身份只读取 `shop_staff`。

## 十、版本规划

- **V1.0(MVP)**：登录(`shop_staff`+风控)、门店上下文+多店切换、工作台、看板(下拉刷新,无轮询)、制作流转(幂等)、扫码+手输核销(多杯确认+防探测)、订单/制作前取消退款(授权员工,必填原因,service门店校验,三项强制)、沽清、营业状态切换
- **V1.1**：库存调整、营收日期范围、**退款阈值告警**、授权多店汇总看板
- **V2.0(待评估)**：交接班/排班、叫号屏投屏、分杯核销、离线缓存

## 十一、验收标准（摘）

- [ ] 登录只读取 `shop_staff`；未注册手机号不发真实验证码；连续失败锁定
- [ ] 移出门店/禁用后旧 Token 立即失效
- [ ] 制作流转 `1→2→3→4` 正确，并发不覆盖；重复请求返回当前状态不报错
- [ ] 扫码核销 1 秒；多杯强制确认总杯数
- [ ] 手输核销码探测被限流；错误模糊；`pickupToken` 不进任何日志
- [ ] 退款必填原因；`refund_ledger` 记 shop_id/operator_id/reason；service 层校验 `order.shop_id==shopId`，跨店退款 403
- [ ] 授权员工可退款（三项强制）；库存调整权限后续通过员工账号/权限组细分
- [ ] 所有员工账号仅能操作明确授权门店，无授权门店时不能登录或操作
- [ ] 小程序不做轮询/声音/振动/订阅消息
