## 二、核心设计决策（必须遵守）

### 2.1 无支付回调

V1.0 只有余额支付，是 **同步** 的：一个 HTTP 请求一个事务完成全部扣款+状态更新。**不需要** 回调接口 `/api/c/order/pay/notify`，不需要支付中（paying）中间态。

### 2.2 下单-支付两步分离

```
第1步: POST /api/c/order/submit  → 创建订单(order_status=0) + 扣库存
第2步: POST /api/c/order/pay/{id} → 余额扣款(order_status→1) + 生成取餐码
```

两步独立事务。不要合并——15分钟支付窗口持有库存锁太久。

### 2.3 三字段订单状态

`biz_order` 使用三个独立字段，永不混合：

| 字段 | 含义 |
|------|------|
| `order_status` | 履约状态：0待支付 1已接单 2制作中 3待取餐 4已完成 5已取消 |
| `pay_status` | 支付状态：0待支付 1成功 2超时 3退款中 4已退款 |
| `refund_status` | 退款状态：0无退款 1处理中 2成功 3失败 |

**支付成功 = 自动接单**：order_status 直接从 0→1，无人工接单步骤。同时写入 `pay_time` 和 `accept_time`。

### 2.4 金额单位

所有金额 **以分为单位（int）**，前端展示时转为元。接口传入/返回全部是分。

### 2.5 规格价格后端重算

**绝对不信任**前端传来的任何价格。下单时后端查询 `product.base_price`/`shop_product.price` + `spec_option.price_add` 重算单价，写入 `biz_order_item` 做完整快照。

### 2.6 支付后用户不可取消

用户仅可取消 `order_status=0, pay_status=0` 的订单。支付后的订单只能由管理员/门店取消（且需全额退款）。

### 2.7 V1.0 整单全额退款

不支持部分退款。每单严格一次整单全额退款，`refund_ledger.uk_idempotent` 防重复。

```sql
-- 在 gogorder_v1_0_business_schema.sql 的 biz_order_item 定义中，
-- product_id 之后增加：
ALTER TABLE `biz_order_item` ADD COLUMN `shop_product_id` BIGINT NOT NULL COMMENT '门店商品ID' AFTER `product_id`;

    "optionId": "opt_abc123",
    "label": "大杯",

### 第2.5步：🆕 修改门店商品删除为纯软删除（R3-P1-1 修订）

`shop_product` 目前物理删除。M08 订单会创建 `biz_order_item.shop_product_id` 引用，物理删除将导致取消/退款时 `restoreStock()` 找不到行。

**🆕 R3-P1-1 决策：V1.0 统一使用软删除（status=0），不再物理删除 shop_product。**

**修改文件 1** — `ProductCenterMapper.xml` 的 `deleteShopProducts`：

```xml
<!-- 改为软删除（保留所有历史引用） -->
<update id="deleteShopProducts">
    update shop_product set status = 0 where id in
    <foreach collection="list" item="id" open="(" separator="," close=")">#{id}</foreach>
</update>
```

**修改文件 2** — `ProductCenterServiceImpl.deleteShopProducts()` 简化：

```java
@Override
@Transactional
public int deleteShopProducts(List<Long> ids) {
    ids = distinctIds(ids);
    if (ids.isEmpty()) return 0;
    // 🆕 检查是否存在进行中的订单引用（仅阻止，不改变删除方式）
    int activeOrderRefs = productCenterMapper.countActiveOrderItemsByShopProductIds(ids);
    if (activeOrderRefs > 0) {
        throw new ServiceException("存在进行中订单引用的门店商品，请先处理订单后再下架");
    }
    // 软删除：status=0
    return productCenterMapper.deleteShopProducts(ids);
}
```

**修改文件 3** — 🆕 重新分配已下架门店商品改为 upsert（修复 `INSERT IGNORE` 静默跳过）：

`ProductCenterMapper.xml` 的 `assignShopProducts`：

```xml
<!-- 原 SQL: insert ignore into shop_product ... -->
<!-- 改为 upsert: -->
<insert id="assignShopProducts">
    insert into shop_product(shop_id, product_id, price, status, stock, sort_order, create_time) values
    <foreach collection="productIds" item="productId" separator=",">
        (#{shopId}, #{productId}, null, 1, -1, 0, sysdate())
    </foreach>
    on duplicate key update status = 1
    <!-- 已存在但已下架(status=0)的记录重新上架；价格/库存/排序保持原值 -->
</insert>
```

> 🆕 R4-P2-2: upsert 的 MySQL affected rows 语义：INSERT → 1，UPDATE → 2。不能再通过 `affected rows` 推断新增数量。Service 层日志改为区分"新分配"与"重新启用"，不依赖行数判断。
>
> 同步修改 `ProductCenterServiceImpl.assignShopProducts()` 日志逻辑：
> ```java
> // 原逻辑: selectAssignedProductIds → 跳过已存在 → 以 affected rows 计新增
> // 改为: 直接调 upsert → 日志记录操作总数（不再区分新增/重新启用）
> log.info("门店商品分配完成 shopId={} productCount={}", shopId, productIds.size());
> ```

**新增 Mapper 方法**（`ProductCenterMapper.java`）：

```java

```

```xml
<select id="countActiveOrderItemsByShopProductIds" resultType="int">
    select count(*) from biz_order_item bi
    inner join biz_order bo on bo.id = bi.order_id
    where bi.shop_product_id in
    <foreach collection="ids" item="id" open="(" separator="," close=")">#{id}</foreach>
    and bo.order_status not in (4, 5)
</select>

**下单核心逻辑 `doSubmitOrder()`**（由 `submitOrder()` 在同一事务内调用）：

```
doSubmitOrder(userId, request):

  // 1. 校验门店
  Shop shop = shopMapper.selectShopById(request.shopId)
  if shop == null or shop.delFlag == 1: throw "门店不存在或已删除"

  // 2. 校验订单类型与门店状态
  if request.orderType == "NORMAL":
      if shop.status != OPEN: throw "当前门店暂不支持即时单"
      if not isInBusinessHours(shop): throw "门店已打烊"
  else if request.orderType == "PREORDER":
      if request.scheduledPickupTime == null: throw "预订单必须选择取餐时间"
      validatePreorderTime(shop, request.scheduledPickupTime)
  else: throw "无效的订单类型"

  // 3. 遍历 items，对每个明细做规格校验和价格重算
  List<BizOrderItem> orderItems = new ArrayList<>()
  int productAmount = 0
  int totalQuantity = 0
  Map<Long, Integer> stockDeductions = new LinkedHashMap<>()

  for each itemRequest in items:
      totalQuantity = Math.addExact(totalQuantity, itemRequest.quantity)
      SpecValidationResult result = specValidationService.validateAndPrice(
          request.shopId, itemRequest.productId, itemRequest.specs)
      if result.stock != -1 and result.stock < itemRequest.quantity:
          throw "商品「" + result.productName + "」库存不足"

      int unitPrice = result.unitPrice
      int subtotal = Math.multiplyExact(unitPrice, itemRequest.quantity)

      BizOrderItem item = new BizOrderItem()
      item.shopProductId = result.shopProductId
      item.productId = itemRequest.productId
      item.productName = result.productName
      item.productImage = result.productImage
      item.specs = JSON.toJSONString(result.selectedOptions)
      item.unitPrice = unitPrice
      item.quantity = itemRequest.quantity
      item.subtotal = subtotal
      orderItems.add(item)

      productAmount = Math.addExact(productAmount, subtotal)
      stockDeductions.merge(result.shopProductId, itemRequest.quantity, Integer::sum)

  // 4. 计算总金额
  int packFee = Math.multiplyExact(shop.packFee, totalQuantity)
  int totalAmount = Math.addExact(productAmount, packFee)

  // 5. 生成订单号
  String orderNo = generateOrderNo()

  // 6. 写入（在 submitOrder() 的 @Transactional 保护下）
  BizOrder order = new BizOrder(...)
  try:
      bizOrderMapper.insertOrder(order)  // useGeneratedKeys 回填 order.id
      orderItems.forEach(item -> item.setOrderId(order.getId()))
      bizOrderItemMapper.batchInsert(orderItems)
  catch DuplicateKeyException e:
      String constraint = parseConstraintName(e)
      if "uk_user_submit_key".equals(constraint):
          // 🆕 R3-P0-3: 查到已有订单后立即返回，不继续扣库存、不继续写明细
          BizOrder existing = bizOrderMapper.selectBySubmitKey(userId, request.getSubmitToken())
          return buildSubmitResponse(existing)
      else if "uk_order_no".equals(constraint):
          // 订单号碰撞 → 重新生成并重试
          order.setOrderNo(generateOrderNo())
          bizOrderMapper.insertOrder(order)
          orderItems.forEach(item -> item.setOrderId(order.getId()))
          bizOrderItemMapper.batchInsert(orderItems)
      else: throw e

  // 7. 按 shopProductId 升序扣库存（🆕 R4-P1-4 防死锁）
  List<Long> sortedIds = new ArrayList<>(stockDeductions.keySet())
  Collections.sort(sortedIds)
  for (Long shopProductId : sortedIds):
      productCenterService.deductStock(order.getId(), shopProductId,
          stockDeductions.get(shopProductId))

  // 8. 返回（🆕 R4-P2-1: 使用 order.getOrderNo() 而非局部变量，覆盖碰撞重试后的新号）
  CUserBalance balance = cUserBalanceMapper.selectByUserId(userId)
  return new OrderSubmitResponse(order.getId(), order.getOrderNo(),
      order.getTotalAmount(), balance != null ? balance.getBalance() : 0, order.getCreateTime())
```

```java
@Service
public class OrderCancelServiceImpl implements IOrderCancelService {

    @Autowired private BizOrderMapper bizOrderMapper;
    @Autowired private BizOrderItemMapper bizOrderItemMapper;
    @Autowired private IProductCenterService productCenterService;
    @Autowired private CUserBalanceMapper cUserBalanceMapper;
    @Autowired private BalanceLedgerMapper balanceLedgerMapper;
    @Autowired private RefundLedgerMapper refundLedgerMapper;

    // 🆕 R2-P0-2: 每笔取消独立事务 REQUIRES_NEW，不受调用方事务影响
    @Override
    @Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRES_NEW)
    public void cancelUnpaidOrder(Long userId, Long orderId) {
        BizOrder order = bizOrderMapper.selectById(orderId);
        if (order == null || !order.getUserId().equals(userId))
            throw new ServiceException("订单不存在");
        if (!order.getOrderStatus().equals(OrderStatusEnum.PENDING_PAY.getCode())
            || !order.getPayStatus().equals(PayStatusEnum.PAY_PENDING.getCode()))
            throw new ServiceException("订单状态不允许取消");

        int rows = bizOrderMapper.cancelOrder(orderId,
            OrderStatusEnum.CANCELLED.getCode(),
            PayStatusEnum.PAY_PENDING.getCode(),  // 用户取消，pay 保持 PENDING
            LocalDateTime.now(), "用户取消");
        if (rows == 0) throw new ServiceException("订单状态已变更");

        restoreOrderStock(orderId);
    }

    @Override
    @Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRES_NEW)
    public void cancelTimeoutOrder(Long orderId) {
        int rows = bizOrderMapper.cancelOrder(orderId,
            OrderStatusEnum.CANCELLED.getCode(),
            PayStatusEnum.PAY_TIMEOUT.getCode(),  // 超时取消
            LocalDateTime.now(), "支付超时自动取消");
        if (rows == 0) return;  // 已被用户支付或取消

        restoreOrderStock(orderId);
    }

    @Override
    @Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRES_NEW)
    public void cancelPaidOrderWithRefund(Long orderId, String cancelReason, Long operatorId) {

        // 1. 锁订单行
        BizOrder locked = bizOrderMapper.selectByIdForUpdate(orderId);
        if (locked == null) throw new ServiceException("订单不存在");

        // 2. 🆕 R2-P1-1: 锁内判断是否已退款 → 幂等返回成功
        if (locked.getRefundStatus().equals(RefundStatusEnum.REFUND_SUCCESS.getCode())) {
            log.info("退款幂等返回 orderId={} 已退款", orderId);
            return;
        }

        // 3. 状态校验：仅已接单+已支付+未退款可退款
        if (!locked.getOrderStatus().equals(OrderStatusEnum.ACCEPTED.getCode())
            || !locked.getPayStatus().equals(PayStatusEnum.PAY_SUCCESS.getCode())
            || !locked.getRefundStatus().equals(RefundStatusEnum.REFUND_NONE.getCode())) {
            throw new ServiceException("订单状态不允许退款");
        }

        // 4. 退款到余额（带乐观锁重试）
        int afterBalance = 0;
        for (int retry = 0; retry < 3; retry++) {
            CUserBalance balance = cUserBalanceMapper.selectByUserIdForUpdate(locked.getUserId());
            int rows = cUserBalanceMapper.updateBalance(
                locked.getUserId(), locked.getTotalAmount(), balance.getVersion());
            if (rows > 0) {
                afterBalance = balance.getBalance() + locked.getTotalAmount();
                // 写余额流水
                BalanceLedger bl = new BalanceLedger();
                bl.setUserId(locked.getUserId());
                bl.setType(BalanceChangeTypeEnum.REFUND.getCode());
                bl.setAmount(locked.getTotalAmount());
                bl.setBeforeBalance(balance.getBalance());
                bl.setAfterBalance(afterBalance);
                bl.setOrderId(orderId);
                bl.setIdempotentKey(orderId + ":balance:REFUND");
                bl.setOperatorId(operatorId);
                balanceLedgerMapper.insert(bl);
                break;
            }
            if (retry == 2) throw new ServiceException("退款失败，请重试");
        }

        // 5. 写 refund_ledger（🆕 R3-P0-2: 唯一键冲突 → 抛异常回滚，不 catch-return）
        //    FOR UPDATE 锁已串行化同订单并发，正常不会走到唯一键冲突。
        //    若发生冲突说明数据已不一致，必须回滚告警。
        RefundLedger refund = new RefundLedger();
        refund.setOrderId(orderId);
        refund.setUserId(locked.getUserId());
        refund.setAmount(locked.getTotalAmount());
        refund.setIdempotentKey(orderId + ":refund");
        refund.setStatus(1);
        refundLedgerMapper.insert(refund);

        // 6. 更新订单状态
        int orderRows = bizOrderMapper.updateOrderForRefund(orderId,
            OrderStatusEnum.CANCELLED.getCode(),
            PayStatusEnum.PAY_REFUNDED.getCode(),
            RefundStatusEnum.REFUND_SUCCESS.getCode(),
            LocalDateTime.now(), cancelReason);
        if (orderRows == 0) throw new ServiceException("订单状态已变更");

        // 7. 按 shopProductId 汇总恢复库存
        restoreOrderStock(orderId);
    }

    // 私有辅助方法：汇总恢复库存（🆕 R4-P1-4 按 shopProductId 升序防死锁）
    private void restoreOrderStock(Long orderId) {
        List<BizOrderItem> items = bizOrderItemMapper.selectByOrderId(orderId);
        Map<Long, Integer> restores = new LinkedHashMap<>();
        for (BizOrderItem item : items) {
            restores.merge(item.getShopProductId(), item.getQuantity(), Integer::sum);
        }
        List<Long> sortedIds = new ArrayList<>(restores.keySet());
        Collections.sort(sortedIds);
        for (Long shopProductId : sortedIds) {
            productCenterService.restoreStock(orderId, shopProductId,
                restores.get(shopProductId));
        }
    }
}

> **关键**：支付事务必须是独立 Spring Bean 的公开方法，否则 Spring AOP 不代理、`@Transactional` 不生效。

```java
package com.ruoyi.system.service.impl;

@Service
public class PaymentTransactionService {

    @Autowired private BizOrderMapper bizOrderMapper;
    @Autowired private CUserBalanceMapper cUserBalanceMapper;
    @Autowired private BalanceLedgerMapper balanceLedgerMapper;
    @Autowired private PaymentLedgerMapper paymentLedgerMapper;

    /**
     * 单次支付尝试。公开方法 + REQUIRES_NEW 确保独立事务。
     * 失败时整个事务回滚（余额回滚、流水回滚、订单状态不变）。
     * 展示号在锁+状态检查之后才生成，幂等请求不消耗编号。
     */
    @Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRES_NEW)
    public PayResponse payAttempt(Long userId, Long orderId, String pickupToken) {

        // 1. 锁订单行
        BizOrder locked = bizOrderMapper.selectByIdForUpdate(orderId);
        if (locked == null) throw new ServiceException("订单不存在");

        // 2. 锁内校验归属
        if (!locked.getUserId().equals(userId)) throw new ServiceException("订单不存在");

        // 3. 锁内判断订单状态。
        // 🆕 R4-P1-1: 仅按 pay_status 判断幂等，不要求 order_status 仍为 ACCEPTED。
        // 订单进入 MAKING/READY/COMPLETED 后重复支付也应返回成功。
        if (locked.getPayStatus().equals(PayStatusEnum.PAY_SUCCESS.getCode())) {
            CUserBalance currentBal = cUserBalanceMapper.selectByUserId(userId);
            return new PayResponse(locked.getOrderNo(), locked.getPickupDisplay(),
                currentBal != null ? currentBal.getBalance() : null);
        }
        if (!locked.getOrderStatus().equals(OrderStatusEnum.PENDING_PAY.getCode())
            || !locked.getPayStatus().equals(PayStatusEnum.PAY_PENDING.getCode())) {
            throw new ServiceException("订单状态不允许支付");
        }

        // 🆕 R4-P1-2: 首次支付路径校验 15 分钟支付有效期
        if (locked.getCreateTime().isBefore(LocalDateTime.now().minusMinutes(15))) {
            // 不在此处取消订单（留给 Quartz 统一处理），仅拒绝支付
            throw new ServiceException("订单已超时，请重新下单");
        }

        // 🆕 R3-P1-2: 仅首次支付路径生成取餐展示号（在锁+状态检查之后）
        LocalDate pickupDate = OrderTypeEnum.PREORDER.getCode().equals(locked.getOrderType())
            ? locked.getScheduledPickupTime().toLocalDate() : LocalDate.now();
        String pickupDisplay = generatePickupDisplay(locked.getShopId(), pickupDate);

        // 4. 锁余额行
        CUserBalance balance = cUserBalanceMapper.selectByUserIdForUpdate(userId);
        if (balance == null) throw new ServiceException("余额账户不存在");
        if (balance.getBalance() < locked.getTotalAmount()) {
            throw new ServiceException("余额不足").setDetailMessage(
                JSON.toJSONString(Map.of("balance", balance.getBalance(),
                    "required", locked.getTotalAmount())));
        }

        // 5. 乐观锁扣减余额（带重试）
        int afterBalance = 0;
        for (int retry = 0; retry < 3; retry++) {
            int rows = cUserBalanceMapper.updateBalance(
                userId, -locked.getTotalAmount(), balance.getVersion());
            if (rows > 0) {
                afterBalance = balance.getBalance() - locked.getTotalAmount();
                break;
            }
            if (retry == 2) throw new ServiceException("系统繁忙，请重试");
            balance = cUserBalanceMapper.selectByUserIdForUpdate(userId);
            if (balance.getBalance() < locked.getTotalAmount())
                throw new ServiceException("余额不足");
        }

        // 6. 写余额流水
        BalanceLedger bl = new BalanceLedger();
        bl.setUserId(userId); bl.setType(BalanceChangeTypeEnum.PAY.getCode());
        bl.setAmount(-locked.getTotalAmount());
        bl.setBeforeBalance(balance.getBalance()); bl.setAfterBalance(afterBalance);
        bl.setOrderId(orderId); bl.setIdempotentKey(orderId + ":balance:PAY");
        balanceLedgerMapper.insert(bl);

        // 7. 写支付流水（🆕 R3-P0-2: 唯一键冲突 → 抛异常回滚，不 catch-return）
        PaymentLedger pl = new PaymentLedger();
        pl.setOrderId(orderId); pl.setUserId(userId);
        pl.setAmount(locked.getTotalAmount());
        pl.setIdempotentKey(orderId + ":pay"); pl.setStatus(1);
        paymentLedgerMapper.insert(pl);
        // 如果抛出 DuplicateKeyException → 事务回滚 → 外层重试时会因步骤3返回幂等成功

        // 8. 更新订单状态（可能因 uk_pickup_token 碰撞抛 DuplicateKeyException）
        int orderRows = bizOrderMapper.updateOrderStatus(orderId,
            OrderStatusEnum.ACCEPTED.getCode(),
            PayStatusEnum.PAY_SUCCESS.getCode(),
            RefundStatusEnum.REFUND_NONE.getCode(),
            LocalDateTime.now(), LocalDateTime.now(),
            pickupToken, pickupDisplay, pickupDate);
        if (orderRows == 0) throw new ServiceException("订单状态已变更");

        return new PayResponse(locked.getOrderNo(), pickupDisplay, afterBalance);
    }
}
```

#### 6.3 `BalanceServiceImpl.java` — 🆕 重试编排（自身无事务）

@Service
public class BalanceServiceImpl implements IBalanceService {

    @Autowired private PaymentTransactionService paymentTx;  // 🆕 注入独立事务 Bean
    @Autowired private BizOrderMapper bizOrderMapper;

    @Override
    public PayResponse pay(Long userId, Long orderId) {

            String pickupToken = generatePickupToken();

                // 🆕 pickupDisplay/pickupDate 在 payAttempt() 事务内、锁之后生成

                        orderId, pickupToken, tokenRetry);

                }
                throw e;
            }
        }
        throw new ServiceException("支付失败，请重试");
    }

**🆕 取餐令牌生成（SecureRandom + DB 碰撞重试）**：

```java
private static final String TOKEN_CHARS = "ABCDEFGHJKLMNPQRSTUVWXYZ23456789";
private static final SecureRandom SECURE_RANDOM = new SecureRandom();
private static final int TOKEN_MAX_RETRIES = 3;

// 🆕 在 pay() 的支付事务内调用。依赖 DB 唯一索引 uk_pickup_token 做最终判断。
// 事务内先执行 INSERT payment_ledger + UPDATE biz_order.set(pickup_token=...)

private String generatePickupToken() {
    StringBuilder sb = new StringBuilder(12);
    for (int i = 0; i < 12; i++) {
        sb.append(TOKEN_CHARS.charAt(SECURE_RANDOM.nextInt(TOKEN_CHARS.length())));
    }
    return sb.toString();
}

**🆕 取餐展示号生成（R3-P0-4: DB 序列表，替换纯 Redis 方案）**：

> 纯 Redis INCR 方案在 Key 过期/重启后从 1 重新开始会导致展示号碰撞。改用 **DB 序列表 + 行锁**，在支付事务内分配，可靠性和事务性均优于 Redis。

**新增表**（追加到 `gogorder_v1_0_business_schema.sql`）：

```sql

    `shop_id` BIGINT NOT NULL,
    `pickup_date` DATE NOT NULL,
    `current_seq` INT NOT NULL DEFAULT 0 COMMENT '当前最大展示号',
    PRIMARY KEY (`shop_id`, `pickup_date`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='取餐展示号序列';
```

**新增 Mapper 方法**（`BizOrderMapper.java`）：

**Java 调用**（在 `PaymentTransactionService` 内，`payAttempt()` 锁+状态检查之后）：

```java

> **为什么不用 Redis**：Redis Key 过期/重启后 INCR 从 1 开始，与 DB 已有展示号碰撞。Redis 异常回退 DB 时 `select max + 1` 无锁保护也不安全。DB 序列表方案利用支付事务已有的行锁，简洁可靠。
>
> **跳号**：事务回滚（令牌碰撞重试）会跳号，接受此代价。V2.0 可升级为独立号段分配服务。

### 第9步：支付超时取消（🆕 Quartz + 分页 + 单订单事务）

**文件位置**：在 `ruoyi-admin` 模块中新建一个 `@Scheduled` 组件，或集成到若依 Quartz 模块。

> 采用若依 Quartz 模块（ruoyi-quartz）：新建 Job 类，通过若依后台「定时任务」管理界面配置 cron 表达式，支持手动触发和日志查看。

```java
package com.ruoyi.quartz.task;

@Component
public class PaymentTimeoutTask {

    private static final Logger log = LoggerFactory.getLogger(PaymentTimeoutTask.class);
    private static final int BATCH_SIZE = 100;

    @Autowired private BizOrderMapper bizOrderMapper;
    @Autowired private IOrderCancelService orderCancelService;

    /**
     * 每分钟执行：扫描超时15分钟的待支付订单。
     * ⚠️ 方法自身不加 @Transactional。
     * 每笔订单在 OrderCancelServiceImpl.cancelTimeoutOrder() 内通过 REQUIRES_NEW 独立事务。
     */
    public void cancelTimeoutOrders() {
        LocalDateTime deadline = LocalDateTime.now().minusMinutes(15);
        Long minId = 0L;
        int totalCancelled = 0;

        while (true) {
            List<BizOrder> batch = bizOrderMapper.selectPendingTimeoutOrders(deadline, minId, BATCH_SIZE);
            if (batch.isEmpty()) break;

            for (BizOrder order : batch) {
                minId = order.getId();
                try {
                    orderCancelService.cancelTimeoutOrder(order.getId());
                    totalCancelled++;
                } catch (Exception e) {
                    log.error("超时取消订单失败 orderId={}", order.getId(), e);
                }
            }
            if (batch.size() < BATCH_SIZE) break;
        }

        if (totalCancelled > 0) {
            log.info("支付超时取消完成，共取消{}笔", totalCancelled);
        }
    }
}
```

```

> **关键设计决策**：
> - 扫描方法不加 `@Transactional`；每笔订单通过 `OrderCancelServiceImpl.cancelTimeoutOrder()` 的 `REQUIRES_NEW` 独立事务
> - 单笔失败记录日志，不终止整批
> - `cancelTimeoutOrder` 与 `cancelUnpaidOrder(user主动取消)` 的区别仅在于 `pay_status` 值：超时设置 `PAY_TIMEOUT(2)`，用户取消保持 `PAY_PENDING(0)`

## 五、关键提示

1. **不要**在下单事务里做支付。两个独立事务。
2. **不要**信任前端价格。后端通过 `ISpecValidationService` 重算 unitPrice。
3. **不要**创建支付回调接口。同步余额支付无回调。
4. **不要**在 `biz_order_item` 中忽略 `specs` 快照——这是后续退款/纠纷的唯一依据。
5. **必须**在取消/超时后恢复库存，按 `shopProductId` 汇总后调用 `restoreStock()`。
6. **必须**所有写余额/库存操作带幂等键 + 唯一约束。
7. 支付成功后**只清空对应门店购物车**，不要把用户其他门店的购物车也清了。
8. 金额全部用**分（int）**，前端展示时才 `/100` 转元。乘加运算使用 `Math.addExact/multiplyExact` 防溢出。
9. **支付幂等必须在事务内订单锁之后判断**：先锁行 → 验归属 → 判状态 → 已支付则返回成功。
10. 所有状态更新 SQL 必须带原状态条件（`WHERE order_status=X AND pay_status=Y`），防止并发覆盖。
11. `packFee` 仅存订单级（整单包装费），V1.0 整单退款够用。V2.0 如需部分退款需重构为 order_item 级拆分。
12. 规格校验和价格计算统一通过 `ISpecValidationService`，购物车和下单共用，杜绝两套逻辑。
