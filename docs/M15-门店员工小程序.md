# M15 - 门店员工小程序（移动端门店运营台）

> 状态：编码中（2026-06-22）。已完成员工登录身份、短信/密码登录、门店上下文后端基础，以及 `gogorder-staff` 登录/工作台首屏；真实短信供应商待接入。本文档实现并移动化 M10 的全部能力，与 M10 共享 `/api/b/` 后端。
> 与 M13 冲突时以 M13 为准。

---

## 1. 概述

门店员工在**微信小程序**上完成本店日常运营：看板、制作流转、通知取餐、订单完成、沽清、退款、营业状态、营收。手机微信打开即用。

**关键定位**：小程序是员工**主动打开**的操作工具，**不承担被动接单提醒**——小程序进后台/锁屏后轮询与声音不可靠，会漏单。接单提醒由两个可靠渠道承担：① PC 看板前台常亮（M10，主渠道）；② 飞鹅打印机支付后自动出单（物理提醒）。小程序仅靠员工主动打开/下拉刷新查看。**不做微信订阅消息、不做轮询/声音/振动提醒**。

**所属端**：B端移动（uni-app，微信小程序 + H5 兜底）+ 后端 `/api/b/`

**优先级**：🔴 高 —— `/api/b/` 尚未实现，本模块是门店端能力的**首次落地**，后端一次设计到位供 M10 复用。

**工程名**：`gogorder-staff`（uni-app，Vue 3，与 C 端 `gogorder-c` 同栈）

## 2. 背景与定位

### 2.1 为什么做小程序（而不是只做 PC 端）

| 维度 | PC/Pad（M10） | 员工小程序（本模块） |
|------|--------------|---------------------|
| 主场景 | 吧台挂屏**常亮**：接单提醒 + 全局看板 + 叫号屏 | 员工手持：出餐扫码、完成订单、沽清、退款 |
| 接单提醒 | ✅ **主渠道**（常亮 + 声音） | ❌ 不承担（后台不可靠） |
| 分发 | 需部署网址/装 Pad | 微信扫码即用，零装机 |
| 出餐扫码 | 摄像头扫码体验一般 | 原生 `scanCode`，用于标签出餐（`2→3`） |
| 中小门店 | 多数没有 Pad | 人人都有手机 |

**结论**：两者互补。PC 看板是接单提醒主渠道，小程序是移动操作工具。

### 2.2 与现有体系的关系

- **复用** M10 §4 的全部 `/api/b/` 接口契约；小程序不另起接口体系。
- **复用** `staff_shop` 门店授权模型（M13 §10）、`X-Shop-Id` 越权防护、订单三状态机（M13 §4）、取餐码双字段（M13 §7）。
- **对齐** 日志规范（成功 info / 幂等 debug / 业务失败 warn / 异常 error，门店操作带 `operatorId`，`pickupToken` 绝不进日志）。

## 3. 用户与门店授权

V1.0 不在 `staff_shop` 里维护每店岗位。员工小程序只认证独立 `shop_staff` 账号，`staff_shop` 只表达"这个员工被授权操作哪些门店"。

### 3.1 授权规则

| 维度 | 规则 |
|------|------|
| 员工身份 | 只读取 `shop_staff`，不接受若依 `sys_user` Token |
| 可操作门店 | `staff_shop` 中该员工关联的门店集合 |
| 默认门店 | 首次授权自动成为默认门店，登录后默认进入该门店 |
| 门店切换 | 只要授权门店数 > 1，即可切换到任一授权门店 |
| 操作权限 | V1.0 以账号启停状态 + 门店授权为准；后续细分权限应设计在员工账号/权限组维度 |

### 3.2 数据范围与越权

- 可见门店 = `staff_shop` 中该员工关联的门店集合；任何员工账号都不能绕过门店绑定。
- "当前操作门店"由前端 `X-Shop-Id` 指定，后端校验 ∈ 可见门店集合，否则 403。
- 跨店接口传 `shopIds`，后端逐个校验 ∈ 授权集合。

## 4. 典型场景（门店一天）

1. **开店**：员工登录 → 工作台点"开始营业"（`RESTING→OPEN`）。
2. **接单制作**：PC 看板/打印机提示新单 → 系统串行自动推进最早订单到"制作中" → 员工做好后点击"通知取餐"（`2→3`）；扫码/手输订单号仅作为兜底 → 自动叫号（`pickup_display`）。
3. **取餐完成**：顾客取走后，员工在订单列表点"完成订单"（`3→4`）；若员工漏点，待取餐 4 小时自动完成，凌晨 4 点兜底归档昨日及更早未完成订单。
4. **沽清**：某品卖完 → "商品"页一键沽清（下架），C 端立刻不可点。
5. **异常处理**：顾客要退 → 订单详情"取消并退款"（授权员工可操作，仅 `order_status=1`，整单全额、每单一次、必填原因，三项强制控制）。
6. **闭店复盘**：店长看"今日营收" → 切"休息"。

> 接单提醒不依赖小程序：员工不打开小程序也能通过 PC 看板/打印机知道有新单。

## 6. 核心业务流程

### 6.1 制作-出餐-完成主流程（对齐 M13 §4.1）

```
支付成功 → order_status=1 待制作（自动接单）
   │ 系统串行自动推进（制作中无单时推进队列最早单）
   ▼
order_status=2 制作中（记 make_start_time）
   │ 通知取餐（主流程：点按钮；兜底：扫码/手输）
   ▼
order_status=3 待取餐（已分配 pickup_display，叫号）
   │ 店员点完成 / 待取餐 4 小时超时 / 凌晨 4 点兜底
   ▼
order_status=4 已完成（归档完成）
```

- 预订单（`PREORDER`）在"预订单"Tab 按 `scheduled_pickup_time` 排序；进入 `make_lead_minutes`（默认 30）窗口后自动落到"待制作"。

### 6.2 通知取餐与完成规则

- **通知取餐（`2→3`）**：制作中订单卡片点击"通知取餐"，后端按 `orderId + shopId` 校验当前门店、已支付、`order_status=2` → 置 `order_status=3`，记录 `complete_make_time`，随后触发自动推进下一单 `1→2`。
- **出餐兜底**：扫码时使用 `pickup_token`；手动时输入订单号 `order_no` 或取餐号 `pickup_display`，进入同样的 `2→3` 流转。
- **订单完成（`3→4`）**：不再扫码核销。店员在订单列表点"完成订单"，或由定时任务自动归档。
- **待取餐 4 小时自动完成**：`PickupTimeoutTask` 每分钟扫描 `order_status=3` 且 `complete_make_time <= now - 4h` 的订单，置为 `4`。
- **凌晨 4 点兜底**：`DailyFinalizeTask` 每天 04:00 扫描昨日及更早仍未完成的 `order_status in (1,2,3)` 订单，统一置为 `4`，用于营业日收尾。

- **安全**：`pickupToken` 仅用于二维码扫码内容，手动输入不要求店员知道 token；日志只记 `pickupDisplay`/`orderNo`，不记录原始 token。

### 6.3 取消退款（对齐 M13 §4.4 / §8.4，审查修订）

- **权限**：授权员工可退（用户确认普通店员也可退）。
- **前置条件**：仅 `order_status=1 且 pay_status=1` 可取消；开始制作（`=2`）后不可退款。
- **门店权限与归属双重校验（service 层）**：先校验独立员工 `operatorId + shopId` 的 `staff_shop` 授权，再锁单校验 `order.shop_id == shopId`；任一不匹配均抛 403。
- **退款控制（V1.0 三项强制 + V1.1 告警）**：
  1. **每单一次整单全额**：`refund_ledger` 幂等键 `{orderId}:refund` UNIQUE 兜底（强制）；
  2. **必填退款原因**：`cancelReason` 为空抛异常，写入订单 `cancel_reason` + 退款流水（强制）；
  3. **不可变审计**：`refund_ledger` 记 `shop_id / operator_id / reason`（强制，谁在哪家店为何退，可追溯）；
  4. **阈值告警**：单店单日退款次数/金额超限 → 推送区域经理/管理员（**V1.1**；V1.0 仅日志监控，可观测但不主动推送）。

> 口径明确：V1.0 实际生效的是「三项强制控制 + 日志监控」，第四项告警在 V1.1。

### 6.4 制作与订单完成流程（2026-06-25 修订：串行，去产能/去核销）

订单从支付到完成的全流程：

```
支付成功 → 待制作(1) →[自动串行推进]→ 制作中(2) →[通知取餐]→ 待取餐(3) →[店员完成/4h超时/凌晨兜底]→ 已完成(4)
```

**制作调度（串行，一次一单）**：
- 门店一次只做一单（串行，**无并发产能概念**）
- 支付成功 → 进队列（待制作 1）；制作中无单时，自动推进队列最早单（`1→2`）
- 推进触发：①通知取餐（`2→3`）后推进下一单；②新单支付成功若制作中无单则直接推进；③定时任务兜底
- 手动「开始制作」按钮若保留，仅作为调试/插急单能力；正式串行调度必须由后端门店级锁保证同店同一时间最多一单制作中

**预计取餐时间**：
- 即时单：`estimated_ready_time = 支付时间 + (前面排队杯数 + 本单杯数) × minutes_per_cup`（串行，每杯 `minutes_per_cup` 分钟，默认 3）
- 预订单：`estimated_ready_time = scheduled_pickup_time`（预约取餐时间）
- 支付成功时算，存 `biz_order.estimated_ready_time`

**通知取餐（`2→3`）**：
- 店员做好后，在制作中订单卡片点"通知取餐" → 订单进入待取餐（`2→3`）+ 自动推进下一单（`1→2`）
- 出餐兜底页可扫码 `pickup_token`，或在 H5/扫码失败时输入订单号/取餐号；接口统一做门店归属、支付状态、订单状态校验；错误模糊化并限流，避免探测有效订单号/token

**订单完成（`3→4`）三途径**（不再扫码核销）：
1. 店员在订单列表点「完成订单」按钮（手动，顾客取走时点）
2. 待取餐 4 小时后自动完成（`PickupTimeoutTask`，每分钟扫描，仅处理 `3→4`）
3. 凌晨 4 点兜底（`DailyFinalizeTask`，扫昨日及更早 `1/2/3→4`）

**定时任务**：
- `PickupTimeoutTask`（每分钟）：待取餐（3）且制作完成超 4 小时 → `3→4`
- `DailyFinalizeTask`（每天凌晨 4 点，cron `0 0 4 * * ?`）：昨日及更早的未完成订单（1/2/3）→ 完成（4），兜底清理

**字段**：
- `biz_order.estimated_ready_time`（预计取餐时间）
- `biz_order.verify_time`：旧字段短期复用为 `3→4` 归档完成时间；后续如新增 `finish_time/completed_time` 再迁移
- `shop.minutes_per_cup` INT DEFAULT 3（单杯制作时间，默认 3 分钟）
- ~~`shop.concurrent_capacity`~~（**去掉**，串行固定一单）

**去掉**：核销接口（verify，`3→4` 扫码）—— 改为通知取餐（`2→3`）和完成订单（`3→4`）；产能配置（`concurrent_capacity`）—— 串行无需。

## 7. 登录与认证方案（独立 `shop_staff`）

**身份基础**：员工账号全部存入独立 `shop_staff`，包含账号、手机号、BCrypt 密码、状态和 `token_version`；与若依 `sys_user` 完全解耦。门店绑定使用 `staff_shop.staff_id`。

| 方案 | 说明 | MVP 取舍 |
|------|------|---------|
| 账号密码 | `/api/b/auth/login/password` 按 `shop_staff.account/password` 校验 | ✅ 兜底，必上 |
| 手机号验证码 | 按 `shop_staff.phone` 查员工，校验状态与 `staff_shop` 后发员工 JWT | ✅ 推荐，主入口 |

- `POST /api/b/auth/login/sms` 使用独立验证码池和员工 JWT，不与 C 端、若依 Token 混用。
- 登录后取 `is_default=1` 门店作为当前门店，写入会话上下文，前端后续请求带 `X-Shop-Id`。
- 店员账号由管理员在 PC 后台创建：先建 `shop_staff`，再写 `staff_shop`（授权门店）；小程序不自助注册。
- **默认门店不落空**：首个门店关联自动设默认；默认门店不可直接取消，必须先把另一家门店设为默认。

**短信登录风控（审查修订，必做）：**

| 项 | 规则 |
|----|------|
| 独立验证码池 | `purpose=STAFF_LOGIN`，与 C 端 `c_user` 验证码隔离，不复用同一码 |
| 发送频率 | 同手机号 60s 内仅 1 次；同 IP 每日上限 N 次（防短信轰炸） |
| 手机号枚举防护 | 未在 `shop_staff` 注册的手机号不落验证码；接口仍返回相同外壳，登录统一提示“账号或验证码错误” |
| 验证码尝试 | 同码错误 5 次立即失效 |
| 一次性消费 | 验证成功立即失效，不可重放 |
| 登录失败锁定 | 同 IP/同账号短时连续失败 N 次 → 临时锁定 M 分钟 |
| 禁用即失效 | 每次请求校验 `shop_staff.status` 与 JWT `token_version`；门店解绑实时校验 `staff_shop` |

## 8. 接口设计

### 8.1 复用 M10 已定义接口（不重写）

| 接口 | 用途 | 小程序是否依赖 |
|------|------|:-:|
| `GET /api/b/order/board` | 看板聚合（preorders/pending/making/waiting） | ✅ 进入/下拉刷新 |
| `GET /api/b/order/{id}/detail` | 订单详情 | ✅ |
| `PUT /api/b/order/{id}/start-make` | 手动开始制作（调试/插急单；默认由系统自动串行推进） | ⚪ |
| `PUT /api/b/order/{id}/notify-pickup` | 通知取餐（制作中订单主流程，`2→3`） | ✅ |
| `PUT /api/b/order/scan-out` | 出餐兜底（body 传 `code`；扫码兼容 `pickupToken`，`2→3`） | ⚪ |
| `PUT /api/b/order/{id}/complete` | 完成订单（`3→4`，顾客取走后店员点击） | ✅ |
| `PUT /api/b/order/{id}/cancel-refund` | 取消并退款（body 必传 `cancelReason`；后端校验门店归属） | ✅ |
| `GET /api/b/order/pending-count` | 待办计数 | ⚪ M10 轮询用；小程序改用 `workbench/today`，不轮询 |
| `PUT /api/b/shop/status` | 营业状态切换 | ✅ |
| `GET /api/b/shop/revenue-today` | 今日营收 | ✅ |

> 所有接口：Header `X-Shop-Id`，后端拦截器校验 `当前员工 + X-Shop-Id ∈ staff_shop`，越权返回 403。

### 8.2 小程序需补充的接口（移动端/未覆盖）

| 接口 | 方法 | 说明 | 权限 |
|------|------|------|------|
| `/api/b/auth/login/sms` | POST | 手机号验证码登录（风控见 §7） | — |
| `/api/b/auth/login/password` | POST | 账号密码登录（若依兜底） | — |
| `/api/b/shop/mine` | GET | 授权门店列表 + 当前门店 + 营业状态 | 全部授权员工 |
| `/api/b/shop/switch` | PUT | 切换当前门店（校验授权） | 授权门店数 > 1 |
| `/api/b/workbench/today` | GET | 工作台首屏聚合：待办计数 + 营业状态 + 今日概览 | 授权员工 |
| `/api/b/shop-product/list` | GET | 本店商品（含库存、上下架状态），沽清页用 | 全部 |
| `/api/b/shop-product/{id}/soldout` | PUT | 沽清/恢复（`status` 0↔1） | 授权员工 |
| `/api/b/shop-product/{id}/stock` | PUT | 库存调整，写 `stock_ledger` ADJUST（带 reason + requestId） | 后续权限组细分 |
| `/api/b/shop/revenue` | GET | 营收（扩展 `revenue-today` 支持日期范围） | 授权员工 |
| `/api/b/area/board` | GET | 授权门店汇总（单量/营收/异常/待制作），支持下钻单店 | 授权多店员工 |
| `/api/b/area/revenue` | GET | 授权门店营收横向对比（按门店/日期） | 授权多店员工 |

> 沽清/库存调整与 `admin/ProductCenterController`（平台级 `/api/admin/`）能力相似，但本接口是**门店级、限定本店、越权校验**的 B 端版本，不能混用。

### 8.3 接口规范与幂等契约（对齐 M13 §15，审查修订）

- 统一响应 `{ code, msg, data }`，分页 `{ code, msg, rows, total }`。
- 金额单位**分**（int）。

**幂等契约（每个写操作必须明确）：**

| 操作 | 幂等机制 | 重复请求行为 |
|------|---------|-------------|
| 自动推进 / 手动开始制作 | 原状态条件 UPDATE（`WHERE order_status=1`）；调度入口加门店级锁 | 已是目标后续状态 → 返回当前状态（成功，不报错） |
| 通知取餐 notify-pickup | `WHERE id=? AND shop_id=? AND order_status=2 AND pay_status=1` | 已通知/已完成 → 成功返回；其他状态 → 业务提示 |
| 出餐兜底 scan-out | `WHERE shop_id=? AND pay_status=1 AND (pickup_token=? OR order_no=? OR active pickup_display=?)`，推进时仍用 `WHERE order_status=2` | 已通知/已完成 → 返回当前订单；不存在/错店/状态不符 → 模糊错误 |
| 完成订单 complete | `WHERE order_status=3 AND shop_id=?` | 已完成 → 返回当前订单；其他状态 → 返回当前状态或业务提示 |
| 自动完成任务 | 条件 UPDATE（4h：仅 `3→4`；凌晨 4 点：昨日及更早 `1/2/3→4`） | 重复扫描无影响 |
| 取消退款 | `refund_ledger` 幂等键 `{orderId}:refund` UNIQUE | 重复 → 返回原退款结果 |
| 库存调整 | `stock_ledger` 幂等键 `adjust:{requestId}`（M13 §8.2） | 重复 → 返回原结果 |
| 沽清 / 营业状态 | 设目标值（`status` 0↔1），天然幂等 | 重复 → 返回当前值 |

> **原则**：状态推进操作用"原状态条件 UPDATE"实现天然幂等，**重复请求返回当前状态而非报错**（弱网点下用户连点不会出错）；资金/库存类用幂等键表。客户端可选传 `requestId` 做操作日志去重。

## 9. 权限与安全

| 项 | 要求 |
|----|------|
| 越权防护 | 每个 `/api/b/` 接口校验 `当前用户 + X-Shop-Id ∈ staff_shop`，跨店操作 403 |
| 权限校验 | V1.0 以账号启停状态 + 门店授权为准；后续如需细分操作权限，在员工账号/权限组维度扩展，不使用每店岗位 |
| **退款门店校验** | service 层先校验独立员工 `operatorId + shopId` 的 `staff_shop` 授权，再锁单校验 `order.shop_id == shopId` |
| 身份边界 | B 端只接受员工 JWT；若依 Token 与 `sys_user` 不进入员工端权限体系 |
| 授权即时失效 | 员工被移出门店后每次请求的 `staff_shop` 校验立即拒绝；账号禁用或资料变更通过 `token_version` 使旧员工 JWT 立即失效 |
| 出餐扫码凭证 | `pickupToken` 不进日志、不下发前端列表（仅二维码扫码时由前端传入）；手动输入使用订单号/取餐号；日志只记 `pickupDisplay`/`orderNo` |
| 出餐防探测 | 手输订单号/取餐号频率限制，扫码 token 同接口限流（同员工同店 ≥10 次/分钟拦截）；错误信息**模糊化**：不区分"码不存在/错门店/状态不符"，统一返回"订单号或取餐号无效或当前不可用" |
| 订单完成 | `3→4` 不再依赖 token；店员按钮、4h 自动完成、凌晨 4 点兜底均走条件 UPDATE |
| 手机号脱敏 | 日志与"我的"页展示走脱敏（对齐 `maskPhone`） |
| Token | 独立员工 JWT，与 C 端 JWT、若依 Token 隔离；员工账号禁用或 `token_version` 变化后旧 Token 立即失效 |
| 防重 | 所有写操作按 §8.3 幂等契约，防弱网点二次提交 |

## 10. 日志与审计（对齐 gogorder 日志规范）

| 事件 | 级别 | 关键字段 |
|------|------|---------|
| 通知取餐成功 | info | `orderId/orderNo/shopId/operatorId/pickupDisplay`（**不记 pickupToken**） |
| 开始制作 / 完成订单 | info | `orderId/orderNo/shopId/operatorId` |
| 自动完成任务 | info | `taskName/orderId/orderNo/shopId/fromStatus/toStatus/reason` |
| 取消退款 | info | `orderId/orderNo/shopId/userId/amount/operatorId/cancelReason` |
| 沽清 / 库存调整 | info | `shopId/shopProductId/operatorId/afterStock` |
| 营业状态切换 | info | `shopId/operatorId/fromStatus/toStatus` |
| 重复出餐 / 幂等命中 | debug | `orderId/shopId/operatorId` |
| 订单号/取餐号无效 / 状态不允许 / 余额不足（退款） | warn | `shopId/operatorId/reason`（reason 模糊，不记 token） |
| 越权访问 / 数据不一致 | error | `userId/shopId/uri` |

> 门店发起的操作一律带 `operatorId`（区别于 C 端自助操作）。退款/出餐失败日志不得含 `pickupToken`。退款审计另由 `refund_ledger.shop_id/operator_id/reason` 不可变记录。

## 11. 非功能需求

| 项 | 要求 |
|----|------|
| **接单提醒** | 小程序**不承担**。渠道：PC 看板常亮（M10）+ 飞鹅打印机支付后自动出单；员工主动打开小程序/下拉刷新查看。**不做微信订阅消息、不做轮询/声音/振动提醒** |
| 看板加载 | 进入页面 + 下拉刷新触发 |
| 弱网 | 操作失败本地保留一次重试；幂等契约保证重复提交无副作用（§8.3） |
| 性能 | 看板聚合 `board` 走 `idx_shop_order_status` 索引；工作台 `workbench/today` 一次拉全 |
| 可用性 | 接口 5xx 不清空已加载看板，保留上次数据 + 错误条 |
| 时区/跨日 | `pickup_date` 区分即时/预约，出餐与完成按门店营业日口径归档 |

## 14. 验收标准

- [ ] 手机号验证码登录只查询 `shop_staff.phone`；未注册手机号不发送真实验证码；连续失败触发锁定
- [ ] 员工被移出门店/禁用后，旧 Token 立即失效
- [ ] 制作流转 `1→2→3→4` 正确，状态并发不覆盖（条件 UPDATE）；重复请求返回当前状态不报错
- [ ] 通知取餐 1 秒完成，`2→3` 后自动推进下一单
- [ ] 手输出餐码高频探测被限流；错误返回模糊信息；`pickupToken` 不出现在任何日志
- [ ] 完成订单 `3→4` 支持店员按钮、待取餐 4h 自动完成、凌晨 4 点昨日及更早 `1/2/3→4` 兜底
- [ ] 制作前取消触发一次整单全额退款；二次被幂等键拦截；退款必填原因；`refund_ledger` 记 shop_id/operator_id/reason
- [ ] 退款 service 层校验 `order.shop_id == shopId`，跨店退款被拒 403
- [ ] 授权员工可退款（带三项强制控制）；库存调整权限后续通过员工账号/权限组细分
- [ ] 沽清后 C 端该商品立刻不可点
- [ ] 营业状态切换实时影响 C 端可下单类型（`RESTING/PAUSED` 仅预订单）
- [ ] 所有员工账号仅可操作 `staff_shop` 明确授权的门店；无授权门店时不能登录或操作
- [ ] 小程序不做轮询/声音/振动/订阅消息；接单提醒由 PC 看板/打印机承担

## 16. 风险与待决策

| 项 | 说明 | 决策 |
|----|------|------|
| `/api/b/` 全新建 | 需新建 `b/` controller、独立员工 JWT 过滤器与 `X-Shop-Id` 拦截器 | 本模块一并交付，作为 M10 的后端基础 |
| 门店授权 | M13 §10 / DB / `StaffShopRequest` / `StaffShopUpdateRequest` 均已改为只维护授权门店与默认门店 | 已落地（代码+schema+文档） |
| 员工登录身份 | 员工端与若依管理账号混用会造成身份、权限和生命周期耦合 | 新建独立 `shop_staff` 主表，账号、手机号、密码、状态和 Token 均不依赖 `sys_user` |
| 退款审计 | `refund_ledger` 原无 shop_id/operator_id/reason，cancelReason 允许 null | 已加三列（NOT NULL）+ 代码必填校验 + service 层门店归属校验 |
| 默认门店 | 原只保证"最多一个默认"，不保证"至少一个" | `StaffShopServiceImpl` 首个关联强制设默认 |
| 退款权限 | 审查建议收紧 vs 用户要求普通店员可退 | 授权员工可退（用户决策），靠三项强制控制 + V1.1 告警兜底 |
| 接单提醒 | 小程序后台不可靠 | **完全不做**轮询/声音/振动/订阅消息；靠 PC 看板常亮 + 打印机出单 |
| 登录方式 | 账号密码 vs 手机号验证码 | 主推手机号验证码（查 `shop_staff.phone`，含 §7 风控）；密码兜底走 `/api/b/auth/login/password` 并强制校验员工状态、门店授权和默认门店 |
| 短信通道复用 | C 端验证码面向 `c_user`，B 端面向 `shop_staff` | 独立 `purpose=STAFF_LOGIN`，不复用同一验证码池 |
| 是否做叫号屏 | 小屏不适合挂墙叫号 | 本模块不做，留给 M10 PC 形态 |
| uni-app vs 原生小程序 | 团队已有 uni-app（C 端） | uni-app，与 C 端同栈 |
